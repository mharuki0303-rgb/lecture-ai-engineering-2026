  - 自分なら解けるか／LLM にとって何が難しいか（メモ）
    - 12907・13236・13453 は、原因の場所が分かれば数行で直せる。自分でも、リポジトリを読み込む時間があれば解けそう。ただし「どのファイルのどの関数か」を巨大なコードベースから探すのがいちばん大変で、LLM にとっても難所は修正そのものより **場所の特定** だと思う
    - 13033 は「エラー文をどう直すか」に正解が 1 つではない。隠しテストがエラー文の文言まで照合していると、正しい方針でも落ちる可能性がある（Verified で除外しようとしている「テストが厳しすぎる」問題の典型に近い）
    - 13398 は天文座標の専門知識（光行差、地心と観測地点中心の違い）が必要で、issue の議論も長い。自分には解けない。LLM も、正しい物理を実装したうえで、既存テストの数値精度に合わせる必要があり難しい
    - 5 件すべて astropy なのは、データが repo 名順に並んでいるため。全体では Django・sympy・scikit-learn など 12 リポジトリから取られている
  - 作成の人数と手順
    - 元の SWE-bench（2,294 件）：論文の著者 7 名が、人気の Python リポジトリ 12 個から「issue を閉じた PR」で、かつテストを追加しているものを機械的に集めて作った。作問した人はおらず、問題文は実際の issue の書き手（OSS の利用者・開発者）が書いたもの
    - Verified（500 件）：OpenAI が SWE-bench の作者と共同で、人手で選び直した部分集合
      - Python の経験がある **プロの開発者 93 人** が、元の test set から無作為に取った **1,699 件** を注釈
      - **1 件につき 3 人** が独立に注釈。見る観点は ①issue の説明が十分か（曖昧すぎないか）、②テストが正しい解答を不当に落とさないか、③解くのにかかる時間（難しさ）
      - ①②は 0〜3 の重大度で付け、3 人のうち誰か 1 人でも 2 以上（重大）を付けたら除外する、という厳しめの規則
      - 結果、1,699 件の約 68% が除外された（説明不足で約 38%、テストの問題で約 61%、重複あり）。残った中から 500 件を選んだ
      - 難しさの内訳は「15 分未満」196 件、「15 分〜1 時間」259 件、「1〜4 時間」42 件、「4 時間超」3 件
    - 採点：LLM 採点ではなく **テストの実行**。モデルのパッチを当てたうえで、FAIL_TO_PASS（直す前は落ち、直した後は通るはずのテスト）と PASS_TO_PASS（もともと通っていて、壊してはいけないテスト）が全部通れば「解決」。Docker のコンテナ環境で実行する

- 気づき・疑問：
  - SWE-bench は「テストで機械的に採点できる」のに、それでも 3 人 × 1,699 件という大きな人手を使っていた。人手が向かう先は「解答の採点」ではなく、**問題とテストそのものが公平か**の確認だった。今日の演習で `rubric.md` の「まだ決めていないこと」を埋めたのも、採点器ではなく基準側を直す作業で、同じ発想だと感じた
  - 3 人のうち 1 人でも重大と言えば落とす、という規則は、今日の「unsure は自動判定から外して人が見る」に近い。評価セットは「割れる問題を入れない」ことで信頼性を上げている。一方、今日の演習では人同士でも割れる問題をわざと入れて、割れることを観察していた。目的（採点器の検証かモデルの比較か）で、割れる問題を入れるかが変わると分かった
  - 除外の約 68% は多く、元の SWE-bench の点数は「モデルが解けない」ではなく「問題が解けない」ものを含んでいたことになる。ベンチマークの数字を見るときは、検証済みの部分集合かどうかを確かめる必要がある
  - 疑問：実在の OSS の issue と修正は公開されているので、モデルの学習データに入っている（汚染）可能性がある。Verified はこれをどう扱っているのか。また 5 件中 4 件が「15 分〜1 時間」で、難しさの偏り（短時間の課題が 9 割）は、最近の高いスコアの解釈にどう効くのかが気になった
  - 注：先頭 5 件の中身は Hugging Face の Dataset Viewer API で確認した（13398 の難しさと 13453 の詳細は要約からで、生データでは未確認）。OpenAI のブログはこの環境から開けなかったため、93 人・1,699 件・約 68% 除外・難しさの内訳などの数字は既知の内容から書いた。提出前にブログで確かめること
